Working well
with Claude Code.

Almost every best practice follows from a single constraint: the context window fills up fast, and performance degrades as it fills.

The constraint that explains the rest

Understand this one, and the eight practices that follow become obvious.

The starting point

Context is the scarce resource

The context window holds your entire conversation: every message, every file read and every command output. A single debugging session or codebase exploration can burn tens of thousands of tokens.

And model performance degrades as context fills. When the window is getting full, Claude may start "forgetting" your earlier instructions or making more mistakes.[1]

What this changes: a long session going off the rails is not a model problem, it is a context problem. Start clean rather than pushing on.

The practices that work

Drawn from Anthropic's internal teams and from engineers using Claude Code day to day.

01

Give it a way to verify its work

This is the one that matters most. Claude stops when the work looks done. Without a check it can run itself, "looks done" is the only signal available — and you become the verification loop: every mistake waits for you to notice it.

Give it something that produces a pass or a fail, and the loop closes on its own: it does the work, runs the check, reads the result, and iterates until the check passes. A test suite, a build exit code, a linter, a script that diffs output against a fixture, a screenshot compared against a design.[1]

The difference: a session you watch, versus one you can walk away from.
02

Ask for evidence, not assertion

Have it show the test output, the command it ran and what it returned, or a screenshot of the result. Reviewing evidence is faster than re-running the verification yourself — and it is what makes a session you did not watch usable at all.[1]

03

Explore, then plan, then code

Letting Claude jump straight to code often produces a clean solution… to the wrong problem. Plan mode separates exploration from execution, in four phases: explore (it reads and answers without changing anything), plan (it drafts a plan you can edit), implement, then commit.[1]

Planning has a cost. For a typo, a log line or a rename, just ask directly. If you could describe the diff in one sentence, skip the plan. It earns its keep when you are unsure about the approach, when the change touches several files, or when you do not know the code being modified.

04

Be specific in the request

Claude can infer intent, but it cannot read your mind. Reference the files, state the constraints, point to an existing pattern to follow. The more precise the instruction, the less you correct afterwards.[1]

Vague prompts keep their use: when you are exploring and can afford to course-correct, a "what would you improve in this file?" surfaces things you would not have thought to ask about.

Configure once, gain every session

Three settings that pay off over time.

05

Write a short CLAUDE.md

/init generates a first file from your repository, to refine from there. Claude reads it at the start of every conversation: shell commands it cannot guess, style rules that differ from the defaults, how to run the tests, branch and PR conventions, architectural decisions, non-obvious gotchas.

And above all what not to put in it: anything Claude can work out by reading the code, standard language conventions it already knows, detailed API documentation (link to it instead), file-by-file descriptions, and self-evident practices like "write clean code".[1]

The test to apply line by line: "would removing this cause Claude to make a mistake?" If not, cut it. A bloated CLAUDE.md makes Claude ignore your actual instructions.
06

The symptom of a file that is too long

If Claude keeps doing something you explicitly forbade, the file is probably too long and the rule is getting lost in it. If it asks you questions that CLAUDE.md already answers, the phrasing is ambiguous.

Treat the file like code: review it when things go wrong, prune it regularly, check it into git so the team contributes. Its value compounds over time.[1]

07

Cut down the permission prompts

By default Claude asks before writing a file or running a command. That is safe but tedious: by the tenth approval you are not reviewing any more, you are clicking. Three ways out — auto mode, where a classifier blocks only what looks risky; an allowlist for commands you know are safe; or sandboxing, which isolates the filesystem and the network.[1]

08

Prefer command-line tools

CLIs are the most context-efficient way to talk to an external service. Install gh if you use GitHub: Claude knows how to use it for issues, pull requests and comments. Without it, it falls back to unauthenticated API calls and hits rate limits.

It also picks up tools it does not know: "use foo --help to learn the tool, then solve A, B, C".[1]
