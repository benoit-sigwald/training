Bien coder
avec Claude Code.

Presque toutes les bonnes pratiques découlent d'une seule contrainte : la fenêtre de contexte se remplit vite, et la qualité baisse à mesure qu'elle se remplit.

La contrainte qui explique tout le reste

Comprenez celle-ci, et les huit pratiques qui suivent deviennent évidentes.

Le point de départ

Le contexte est la ressource rare

La fenêtre de contexte contient toute votre conversation : chaque message, chaque fichier lu et chaque sortie de commande. Une seule session de débogage ou d'exploration peut consommer des dizaines de milliers de jetons.

Or la performance d'un modèle se dégrade à mesure que le contexte se remplit. Quand la fenêtre approche de la saturation, Claude peut « oublier » vos consignes du début ou multiplier les erreurs.[1]

Ce que ça change : une session longue qui part en vrille n'est pas un problème de modèle, c'est un problème de contexte. Redémarrez propre plutôt que d'insister.

Les pratiques qui marchent

Tirées des équipes internes d'Anthropic et des ingénieurs qui utilisent Claude Code au quotidien.

01

Donnez-lui un moyen de vérifier son travail

C'est la pratique qui compte le plus. Claude s'arrête quand le travail a l'air fini. Sans contrôle qu'il puisse exécuter lui-même, « a l'air fini » est le seul signal disponible — et c'est vous qui devenez la boucle de vérification : chaque erreur attend que vous la remarquiez.

Donnez-lui quelque chose qui produit un succès ou un échec, et la boucle se referme toute seule : il fait le travail, lance le contrôle, lit le résultat, et recommence jusqu'à ce que ça passe. Une suite de tests, un code de sortie de build, un linter, un script qui compare une sortie à un fichier de référence, une capture d'écran comparée à une maquette.[1]

La différence : une session que vous surveillez, contre une session dont vous pouvez vous éloigner.
02

Demandez les preuves, pas l'affirmation

Faites-lui montrer la sortie des tests, la commande lancée et ce qu'elle a renvoyé, ou une capture du résultat. Relire une preuve est plus rapide que refaire la vérification vous-même — et c'est ce qui rend exploitable une session que vous n'avez pas regardée.[1]

03

Explorer, puis planifier, puis coder

Laisser Claude se jeter sur le code produit souvent une solution propre… au mauvais problème. Le mode plan sépare l'exploration de l'exécution, en quatre temps : explorer (il lit et répond sans rien modifier), planifier (il rédige un plan que vous pouvez éditer), implémenter, puis commiter.[1]

Le plan a un coût. Pour une faute de frappe, une ligne de log ou un renommage, demandez directement. Si vous pouvez décrire le diff en une phrase, sautez le plan. Il devient utile quand vous doutez de l'approche, quand le changement touche plusieurs fichiers, ou quand vous ne connaissez pas le code concerné.

04

Soyez précis dans la demande

Claude devine l'intention, il ne lit pas dans les pensées. Citez les fichiers, donnez les contraintes, montrez un exemple existant à imiter. Plus l'instruction est précise, moins vous corrigerez ensuite.[1]

Les demandes vagues gardent leur usage : quand vous explorez et que vous pouvez vous permettre de corriger le tir, un « qu'est-ce que tu améliorerais dans ce fichier ? » fait remonter des choses auxquelles vous n'auriez pas pensé.

Cadréécris un test pour foo.py qui couvre le cas où l'utilisateur est déconnecté. évite les mocks.

Trois réglages qui changent la donne sur la durée.

05

Écrire un CLAUDE.md court

/init génère un premier fichier à partir de votre dépôt, à affiner ensuite. Claude le lit au début de chaque conversation : commandes shell qu'il ne peut pas deviner, règles de style qui s'écartent des conventions, façon de lancer les tests, conventions de branche, décisions d'architecture, pièges non évidents.

Et surtout ce qu'il ne faut pas y mettre : ce que Claude peut trouver en lisant le code, les conventions standard du langage, la documentation d'API détaillée (mettez un lien), les descriptions fichier par fichier, et les évidences du genre « écrire du code propre ».[1]

Le test à s'appliquer, ligne par ligne : « est-ce que retirer cette ligne ferait faire une erreur à Claude ? » Si non, coupez. Un CLAUDE.md trop long fait ignorer vos vraies consignes.
06

Le symptôme d'un fichier trop long

Si Claude continue à faire une chose que vous avez explicitement interdite, le fichier est probablement trop long et la règle se perd dedans. S'il vous pose des questions dont la réponse est dans CLAUDE.md, c'est la formulation qui est ambiguë.

Traitez ce fichier comme du code : relisez-le quand ça se passe mal, élaguez-le régulièrement, versionnez-le dans git pour que l'équipe y contribue. Sa valeur se cumule avec le temps.[1]

07

Réduire les demandes de permission

Par défaut, Claude demande l'autorisation avant d'écrire un fichier ou de lancer une commande. C'est sûr, mais fastidieux : à la dixième validation, vous ne relisez plus, vous cliquez. Trois façons de sortir de là — le mode automatique, où un classifieur ne bloque que ce qui paraît risqué ; une liste d'autorisations pour les commandes que vous savez sûres ; ou le bac à sable, qui isole le système de fichiers et le réseau.[1]

08

Préférer les outils en ligne de commande

Les CLI sont la façon la plus économe en contexte de parler à un service externe. Installez gh si vous utilisez GitHub : Claude sait s'en servir pour les issues, les pull requests et les commentaires. Sans lui, il passe par l'API sans authentification et se fait limiter.

Il apprend aussi vite les outils qu'il ne connaît pas : « utilise foo --help pour apprendre l'outil, puis résous A, B, C ».[1]
